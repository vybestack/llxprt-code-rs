# Plan: Extensible model APIs and OpenAI Responses/Codex support

## Objective

Replace the direct `OpenAIChatModel` dependency in `src/adapter.rs` with a typed construction boundary. Add the OpenAI Responses and Codex HTTP capabilities currently present in vendored SerdesAI, after repairing the parts that do not satisfy LLxprt's multi-round and fail-fast contracts.

The completed design must support these paths without provider or API selection in the agent loop:

| Provider | Model API | Transport | Credential | Initial status |
| --- | --- | --- | --- | --- |
| OpenAI, OpenAI Vercel, OpenAI-compatible | Chat Completions | HTTP | API key | Existing behavior |
| OpenAI | Responses | HTTP | API key | Add in this issue |
| OpenAI Responses (`openai-responses`) | Responses | HTTP | API key | Add as LLxprt Code compatibility alias |
| Codex | Responses | HTTP | OAuth | Add in this issue |

The construction key includes transport so later WebSocket work can add a registration without changing the adapter or agent loop. This issue does not implement WebSocket. Anthropic remains unsupported, but provider-specific endpoint, credential, request-setting, and system-prompt behavior must belong outside `src/adapter.rs` so Anthropic can be added without restructuring the host.

## Non-goals

- OpenAI Responses WebSocket transport
- OAuth login or token refresh
- Anthropic support
- Stateful `previous_response_id` continuation
- Persistence of provider response ids, encrypted reasoning state, or socket state
- OpenAI built-in tools such as web search, code interpreter, file search, image generation, or MCP
- Automatic fallback between APIs, providers, credentials, or transports
- Model-name-based API inference

## Architecture decisions

### 1. Typed model target

Add a model API module with these concepts:

- `ProviderId`: initially exact provider strings `openai`, `openai-responses`, `openaivercel`, `openai-compatible`, and `codex`. The sibling alias-provider factory accepts `openai-vercel` as an integration `baseProvider`, but its saved-profile runtime normalizer and creation wizard emit `openaivercel`. Rust accepts only that persisted profile spelling; a profile using `openai-vercel` rejects.
- `ModelApi`: Chat Completions and Responses.
- `TransportKind`: HTTP in this issue. WebSocket can be added by its separate change.
- `ModelTarget`: the exact provider, API, and transport tuple.

Profile values are parsed once into these types. `TransportKind::Http` is the only value the resolver can produce in issue 1; no profile key selects transport, and every supported provider/API resolution returns HTTP. Code after profile resolution must not compare provider or API strings.

Use LLxprt Code's persisted `ephemeralSettings.apiMode` setting with exact lowercase, untrimmed values `chat` and `responses`. Unlike LLxprt Code's normalization, surrounding whitespace or different case rejects. Also parse existing selectors `responsesMode` and `responses-mode` with those same exact-value rules. Valid selectors use LLxprt Code's precedence: `apiMode`, then `responsesMode`, then `responses-mode`; a lower-priority valid value does not affect the selected higher-priority value, including when they disagree. An explicit empty, wrong-type, or unknown value fails instead of falling through, preserving this project's fail-fast rule even though LLxprt Code skips stale selector values. `openaiResponsesEnabled` is a separate validated boolean accepted as inert metadata. This is a deliberate divergence: LLxprt Code uses it to force Responses on non-official base URLs, while this binary never lets it select an API because target selection is exclusively typed and explicit. `apiMode` is the documented setting for new profiles. Compatibility selectors are supported only to read existing LLxprt Code profiles and are not emitted by this binary.

Compatibility behavior:

- Omitted selectors for OpenAI, OpenAI Vercel, and OpenAI-compatible mean Chat Completions.
- Provider `openai-responses` resolves to Responses. Any explicit selector must agree.
- Omitted selectors for provider `codex` mean Responses so the existing `gpt56solhigh` profile works without model-name inference.
- Explicit malformed or provider/API-incompatible values fail. Lower-priority valid selector disagreement follows precedence and is not an error.
- Codex plus Chat Completions fails before credential access.
- Anthropic remains unsupported and causes zero network requests.

### 2. API-specific resolved configuration

Refactor `ModelConfig` so invalid combinations cannot be represented casually:

- `ModelTarget`
- validated model identifier
- API-specific validated endpoint
- credential enum containing either an API-key credential or a Codex OAuth credential
- API-specific request settings
- host-side context limit

Use separate finalized `StandardOpenAiChatSettings`, `DsflashChatSettings`, `OpenAiResponsesSettings`, and `CodexResponsesSettings` types, plus private parsed drafts for the two Responses types whose cache fields depend on invocation context. ### 3. Small static construction registry

Use one static table of exact `ModelTarget` registrations. Its constructor identifiers are `construct_openai_chat_http`, `construct_openai_responses_http`, `construct_openai_vercel_chat_http`, `construct_openai_compatible_chat_http`, and `construct_codex_responses_http`. Each accepts validated configuration and returns a neutral constructed model. The complete issue 1 production table uses five constructors for six registrations, with both OpenAI Responses provider spellings sharing the same function pointer:

| Provider | API | Transport | Constructor |
| --- | --- | --- | --- |
| OpenAI | Chat Completions | HTTP | `construct_openai_chat_http` |
| OpenAI | Responses | HTTP | `construct_openai_responses_http` |
| OpenAI Responses | Responses | HTTP | `construct_openai_responses_http` |
| OpenAI Vercel | Chat Completions | HTTP | `construct_openai_vercel_chat_http` |
| OpenAI-compatible | Chat Completions | HTTP | `construct_openai_compatible_chat_http` |
| Codex | Responses | HTTP | `construct_codex_responses_http` |

OpenAI Responses plus Chat, OpenAI Vercel plus Responses, OpenAI-compatible plus Responses, Codex plus Chat, and every unlisted tuple fail before credentials. Registry lookup requires exactly one match:

- zero matches: bounded unsupported-target error
- one match: construct the model
- duplicate matches: construction error and unit-test failure

Do not add a plugin loader or a factory trait until construction requires state that function pointers cannot express.

The construction result contains:

- `Arc<dyn serdes_ai::models::Model>`
- prevalidated Serdes request settings
- `PromptPolicy { legacy_reasoning_effort_note: Option<ProfileReasoningEffort> }`

Define host-owned `ProfileReasoningEffort::{Minimal, Low, Medium, High, XHigh, Max}` with exact `as_str()` spellings `minimal`, `low`, `medium`, `high`, `xhigh`, and `max`; do not import it as Serdes `ReasoningEffort`. The exact prompt-note suffix uses `as_str()`. OpenAI Responses validates the value into the closed subset `{Low, Medium, High}` and then uses an exhaustive subset conversion to `serdes_ai::models::openai::ReasoningEffort::{Low, Medium, High}`; the other three host variants are unreachable in that settings type by construction. Dsflash maps all six variants exhaustively into a new vendored `ChatTemplateReasoningEffort` enum with the same six serialized spellings. Codex requires `ProfileReasoningEffort::High` and exhaustively maps that singleton accepted subset to typed vendored `CodexReasoningEffort::High`, serialized as `high`, rather than carrying a free string. Per-variant conversion and rejection tests pin each boundary.

The registration constructor sets the prompt policy solely from the resolved settings type. `StandardOpenAiChatSettings` sets the typed optional effort when `reasoning.effort` is present and otherwise sets `None`; `DsflashChatSettings`, `OpenAiResponsesSettings`, and `CodexResponsesSettings` always set `None`. Agent construction formats `Some(effort)` exactly as `reasoning effort requested by profile (prompt note only): <effort>` and sets the existing public `CodingAgent::prompt_notes` field. The closed effort enum makes every generated note shorter than the existing 1,024-byte `MAX_PROMPT_NOTE_BYTES`; exact per-variant tests assert that bound. Delete `CodingAgent::prompt_reason_note` and its profile-map/over-cap substitution tests because the untyped `EphemeralSettings::prompt_notes` source disappears. The public field and its external direct-override behavior remain unchanged, including existing overall prompt/materialization limits; the CLI passes the typed policy through `AgentRuntimeConfig` and never rereads the profile. The agent does not inspect `ModelTarget`, provider, API, or chat variant.

Typed wire-setting ownership is per constructed vendored model, not `ModelSettings.extra`. `StandardOpenAiChatSettings` maps only common Serdes fields into the adapter's ordinary `ModelSettings`; it constructs `OpenAIChatModel` with new typed `OpenAIChatModelRequestSettings { chat_template_kwargs: None }`. `DsflashChatSettings` constructs the same model with `chat_template_kwargs: Some(ChatTemplateKwargs { enable_thinking, reasoning_effort: Option<ChatTemplateReasoningEffort> })`; the model stores this typed request-extension settings value and its request builder copies it into `ChatCompletionRequest`. `OpenAiResponsesSettings` converts into the existing per-model `OpenAIResponsesModelSettings`, extended with typed `text_verbosity`, `prompt_cache_key: Option<OpenAIResponsesPromptCacheKey>`, and `prompt_cache_retention`; construction always sets `send_reasoning_ids: false` and `previous_response_id: None`, and the request builder forces `store: false`. `CodexResponsesSettings` converts into a new vendored `ChatGptOAuthRequestSettings { reasoning: Option<CodexReasoning { effort: CodexReasoningEffort, summary: CodexReasoningSummary }>, text_verbosity: CodexTextVerbosity, session_id: ChatGptSessionId, prompt_cache_key: Option<ChatGptPromptCacheKey> }`, passed through a typed `ChatGptOAuthModel::with_request_settings` builder distinct from public loopback-only `ChatGptConfig`; the Codex request builder reads only that typed value and omits the entire `reasoning` object when the option is `None`. `OpenAIResponsesPromptCacheKey`, `ChatGptPromptCacheKey`, and `ChatGptSessionId` are vendored bounded opaque newtypes. Host `ProviderSessionId` is crate-private, is constructed only from exact validated `SessionId` bytes, and converts explicitly to always-present `ChatGptSessionId` plus `PromptCacheKey`; cache policy then converts the key to the selected optional vendored prompt-cache newtype. No vendor crate depends on a host type and no unvalidated profile string enters any conversion. Each registration consumes its finalized host settings once during model construction, leaving the neutral adapter with the model and ordinary Serdes `ModelSettings` only.

Production always constructs `ModelSettings { extra: None, .. }`. No issue-1 vendored model reads `ModelSettings.extra`; direct poisoned-extra tests pass a nonempty object to each Chat, OpenAI Responses, and Codex request builder and prove it changes no serialized request field. Host construction tests assert `extra.is_none()`. This forbids an untyped escape route while retaining the existing public Serdes field for compatibility.

### 4. Neutral adapter and agent loop

Rename the behavioral seam from `ChatBackend` to `ModelBackend`. Preserve a public alias for current consumers and tests.

`ModelAdapter` stores a Serdes model trait object and prevalidated settings. It maps Serdes responses into LLxprt results. It does not import concrete OpenAI models and does not select a provider, API, transport, endpoint, or credential.

`CodingAgent` receives a constructed backend. Its round loop, tool execution, limits, persistence, and replay remain API-neutral. Preserve the 16-call per-turn cap, 32-round cap, and existing argument, output, assistant, request, and response byte caps. Add an optional integer `max_output_bytes` argument to both `read_file` and `search_file_content`, accepted from 256 through `MAX_TURN_OUTPUT_BYTES` (16,777,216). For search, define the whole-output limit once as `min(requested_or_ToolConfig.max_output_bytes, ToolConfig.max_output_bytes, remaining_turn_budget, MAX_SEARCH_RESULT_BYTES)`. Omission therefore preserves the current `min(ToolConfig.max_output_bytes, remaining_turn_budget, MAX_SEARCH_RESULT_BYTES)` whole-output ceiling; production initializes the tool-config term to `MAX_TURN_OUTPUT_BYTES`, while override fixtures retain their lower or higher explicit value. In the production-reachable domain, `whole_output_limit <= MAX_TURN_OUTPUT_BYTES < MAX_SEARCH_DATA_BYTES`, omission sets `data_limit = whole_output_limit` and preserves current data/rendering except at exact fill: changing `SearchCounters` from the larger static ceiling to `>= data_limit` newly records `result_bytes`, and final rendering reserves room for its truncation note. Removing the separate static ceiling intentionally changes only test/configuration states above `MAX_TURN_OUTPUT_BYTES`; at `max_output_bytes = MAX_SEARCH_RESULT_BYTES`, the new omission data ceiling is 128 bytes larger than the old `MAX_SEARCH_DATA_BYTES`. When an explicit per-call cap is strictly smaller than each other term and therefore is the unique binding term, reserve `MAX_SEARCH_NOTE_BYTES` once inside that requested whole-output ceiling by setting `data_limit = whole_output_limit.saturating_sub(MAX_SEARCH_NOTE_BYTES)`. If the requested value ties or exceeds another binding term, use the omission-path `data_limit = whole_output_limit`; final rendering still truncates data to fit a note as it does today. This makes increasing an explicit cap monotonic and confines the 128-byte early reservation to a cap that actually reduces output. In `src/tools/search.rs`, retain `SearchSpec.result_data_limit` as the single owner of the computed `data_limit`; change only the static-ceiling checks by passing that value into `SearchCounters::stopped()` and `SearchCounters::add_result()`. Keep `push_search_result`'s existing limit parameter and forward the same value to `add_result`; do not redesign its truncation algorithm. Remove `MAX_SEARCH_DATA_BYTES` from `src/tools.rs` and its imports because every former static comparison now receives the dynamic value. Retain final rendering's existing `MAX_SEARCH_RESULT_BYTES.min(max_output_bytes)` bound and truncation-note accounting so data plus any note never exceeds `whole_output_limit`. For read, define the whole-output limit as `min(requested_or_ToolConfig.max_output_bytes, ToolConfig.max_output_bytes, remaining_turn_budget)`; omission preserves the current `min(ToolConfig.max_output_bytes, remaining_turn_budget)` behavior. Its range header, raw content window, and truncation marker together fit the effective limit. After `scrub_secrets`, the agent UTF-8-truncates the scrubbed result to the minimum of the pre-scrub tool-result byte length and remaining turn budget, so replacement growth cannot exceed the tool's effective per-call cap. Tests use repeated short secrets whose `[redacted]` replacements expand the string and prove this post-scrub bound. A requested per-call cap governs only a successfully parsed and dispatched tool result. JSON/schema/range/unknown-argument failures occur before dispatch and return a fixed value-free diagnostic capped at 1,024 UTF-8 bytes; they never echo the arguments or enter the successful-tool-output arithmetic. The Phase 10 prompt requires each tool call to request a 4,096-byte whole-output cap, and acceptance verifies those arguments; a malformed call is model noncompliance rather than a capped successful result.

For the reachable forced-finalization ordering after 16 sequential one-call rounds, the final preflight has 36 requests and 36 parts: one system, one initial user, 16 assistant tool-call responses, 16 tool returns, one empty-text call-free assistant response, and one fixed final-summary user request. The acceptance fixture drives the real round loop with 16 distinct 256-byte call ids, each consisting of 255 ASCII `A` bytes followed by one distinct ASCII letter `A` through `P`, and the longest registered executable tool name, `search_file_content` at 19 bytes. This satisfies the host's turn-scoped uniqueness check and reaches forced finalization. The live acceptance script checks `[A-Za-z0-9_-]{1,256}` from the completed transcript; the host itself enforces only nonempty, unique, at-most-256-byte ids. An id outside the acceptance regex is a model-compliance failure and is excluded from this acceptance-specific category arithmetic, whose category caps are conditional on that checked compliance constraint; the separate production estimator and preflight still evaluate the actual serialized id. The category caps deliberately over-count tool names at the 64-byte `MAX_TOOL_NAME_BYTES` validator ceiling, maximally escaping complete 4,096-byte read/search outputs, maximally escaping 512-byte normalized valid-JSON arguments, 512-byte round-level assistant strings, and fixed timestamps. It measures three disjoint serialized categories: the initial system/user request parts, fixed final-summary user part, and `crate::adapter::estimate_tool_schema_bytes` for the exact enabled non-shell tools, capped at 131,072 bytes; 17 complete `ModelRequestPart::ModelResponse` envelopes, including the empty terminal response, metadata, text, normalized arguments, ids, and escaping, capped at 131,072 bytes; and 16 complete `ModelRequestPart::ToolReturn` values, including `part_kind`, tool name, call id, timestamp, framed content, quotes, and escaping, capped at 420,000 bytes. The fixed and structural estimator overhead is exactly `8,192 + 36 * 512 + 36 * 128 = 31,232` bytes. The category sum is therefore at most 713,376 bytes, leaving 73,056 bytes below the `gpt56solhigh` 786,432-byte materialization budget. The test also asserts that the production quantity `estimate_request_bytes(requests).saturating_add(crate::adapter::estimate_tool_schema_bytes(tools))` is no greater than both 713,376 and the production budget. If any measured category exceeds its bound, stop, narrow the acceptance protocol, revise this plan, and obtain a new independent `PASS`; do not raise a cap silently. A smaller normal-final-assistant fixture and a separate over-budget fixture cover the other paths. Existing general assistant and argument caps remain unchanged outside this acceptance protocol. Exact, boundary, UTF-8, range-header, truncation-note, budget-interaction, and schema tests cover both output-cap arguments.

Provider-specific system-prompt mapping belongs in the provider/API implementation or its registration, not in `src/adapter.rs`. Codex must send the host's assembled system prompt exactly once as `instructions`. It must not replace it with bundled text or inject it as a synthetic user message. Future Anthropic OAuth behavior will be added through its own provider registration and prompt mapper.

Keep `PromptPolicy` limited to the one active typed optional effort required now. Do not add variants for future providers. Additional prompt behavior belongs to a provider registration and extends this typed policy only when an active registration needs it.

### 5. Endpoint ownership

Each API owns route validation and derivation:

- Chat accepts the existing origin, `/v1`, and exact chat-completions forms.
- OpenAI Responses accepts origin, `/v1`, and exact responses forms, then produces one `/responses` suffix.
- Codex production use is pinned to `https://chatgpt.com/backend-api/codex`. Its profile must contain `base-url`; before URL parsing, inspect the bounded raw authority and reject any explicit port token, including `:443`, because `url::Url` normalizes a default port away. Then parse an absolute HTTPS URL with no userinfo, query, or fragment, and require host `chatgpt.com` plus path `/backend-api/codex` after removing trailing slashes. ### 7. Reasoning and session boundary

The issue uses a stateless, full-history HTTP policy:

- Send configured reasoning effort and summary request settings.
- Validate and bound returned reasoning summary parts, then discard them from the user-facing answer and durable transcript.
- Discard provider reasoning ids and encrypted reasoning content.
- Never place reasoning ids, encrypted content, or summary text in subsequent requests, session files, diagnostics, stdout, or stderr.
- Persist only assistant text, function calls, original valid provider argument text, and tool results. Provider-response mapping and direct vendored tests preserve malformed text long enough for host validation, but malformed production arguments fail before tool execution or replay persistence. Replay/request materialization parses and may normalize valid JSON; no contract promises byte-identical valid argument text after replay.
